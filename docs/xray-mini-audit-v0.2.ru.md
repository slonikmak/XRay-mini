## Вердикт

**Это содержательный прототип, но спецификация v0.2 пока не выполнена. Приёмку MVP закрывать рано.**

Основные проблемы — не в оформлении интерфейса: контракт импорта и маршрутизации отличается от спецификации; нет проверяемой версии Xray; не реализована очистка runtime-файлов после аварии; гарантии завершения child process имеют известное окно; вместо single-writer Manager использована mutex-модель. Отдельно не подтверждены запуск на Windows и три реальные транспортные комбинации.

README прямо сообщает, что первоначальный полный текст спецификации был недоступен и основа восстанавливалась по обсуждению. Это объясняет расхождения, но не меняет критерии приёмки. Источник: [README.md:80–82](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/README.md#L80-L82).

В этом отчёте **«не реализовано»**, **«реализовано иначе»** и **«не проверено»** — разные оценки. Не обнаружена причина считать всякую mutex-архитектуру ошибочной; не доказана неработоспособность REALITY/XHTTP; зафиксировано отсутствие соответствия конкретным согласованным требованиям и проверкам.

## Методика и результаты запуска

Код и метаданные коммита прочитаны через подключение GitHub. Для локального тестирования использован доступный архив `xray-mini-prototype.zip`. После исключения дополнительных `bin/` и `frontend/dist/` вычисленный Git tree исходников **в точности совпал** с деревом указанного коммита. Следовательно, тестировался тот же исходный код, а не предположительно похожая старая версия.

### Что независимо выполнено

- Все 14 исходных backend-тестов прошли **дважды с race detector**: `go test -race -v -count=2 .` для неизменённого `internal/core`.
- `go vet` того же core завершился успешно.
- Core вместе с тестами успешно кросс-компилирован под Windows amd64; **Windows-исполнение не производилось**.
- Добавлены только в изолированную проверочную копию пять тестовых функций, включающих семь сценариев требований. Все семь обнаружили расхождения. Файл `review_spec_v02_test.go` приложен отдельно; production-код не изменён.

**Важная граница:** перечисленные Go-проверки выполнялись на доступном **Go 1.23.2 / Linux**, в отдельном минимальном модуле, с побайтно неизменёнными файлами `internal/core`. Исходный проект требует Go 1.26.10 и Wails 3.0.0; их полную сборку я не воспроизвёл. Скачивание toolchain завершилось ошибкой DNS, а `npm ci --offline` — `ENOTCACHED`. Это ограничения окружения проверки, а не установленная ошибка проекта. Изолированный core использует стандартную библиотеку и смог пройти эти проверки без внешних зависимостей.

### Что не подтверждено этим ревью

Полная сборка Wails, frontend typecheck/Vitest, работа WebView2, Windows DPAPI/DACL/Job Object в исполнении, реальные SOCKS5/HTTP-запросы через Xray, REALITY-handshake, XHTTP/TLS и проверки принудительного завершения GUI. Предыдущие успешные сборки и frontend-тесты описаны в [docs/VERIFICATION.md](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/docs/VERIFICATION.md); это свидетельство репозитория, **не мой независимый повторный прогон**. Сам документ также явно перечисляет отсутствие Windows runtime и Xray e2e проверок.

## REVIEW-01 · P1 · Импорт и runtime допускают обход VLESS

**Требования:** FR-02, FR-03, FR-04, связанные acceptance criteria.

**По спецификации:** ровно один целевой VLESS outbound со `streamSettings`; дополнительные секции не копируются молча; runtime имеет собственные два inbound и явную маршрутизацию через выбранный VLESS, без direct-обхода.

**По коду:** `PrepareConfig` проверяет только непустой массив `outbounds` и наличие непустого поля `protocol` в каждом элементе. Не требует `vless`, `streamSettings` или однозначного выбора. Сохраняет все outbounds и исходные `routing`/`dns`/`policy`; меняет лишь `inbounds` и `log`.

Источник: [internal/core/config.go:20–43](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/config.go#L20-L43).

**Воспроизведено локально:** принят профиль только с `freedom`; приняты два VLESS; принят VLESS без `streamSettings`; в runtime сохранены `freedom` и правило, направляющее `socks-in`/`http-in` в `direct`; для одного VLESS не создаётся собственный `routing`.

**Последствие:** можно получить рабочий локальный прокси и положительный health-check без прохождения через нужный VLESS-сервер. Это вывод из сохранённой конфигурации и правил Xray, **а не заявление о проведённом сетевом e2e**. Официальная документация Xray описывает выбор первого подходящего routing-правила, а при отсутствии совпадения — первого outbound; `freedom` является прямым выходом. README проекта также прямо предупреждает, что проверка может уйти напрямую.

**Исправление:** разделить импорт исходника и построение runtime; выбрать ровно один VLESS со `streamSettings`; отклонять неоднозначность; показывать пользователю, какие секции отброшены; создавать фиксированный outbound tag и собственные правила для обоих локальных inbound. Нельзя просто копировать пользовательские routing/direct-правила. Зависимости выбранного outbound от дополнительных тегов/локальных ресурсов следует либо явно поддержать, либо отклонить, а не оставлять сломанные ссылки.

**Проверка исправления:** тесты на отсутствие VLESS, два VLESS, отсутствие `streamSettings`, сохранение параметров трёх нужных transport/security-комбинаций, предупреждение об отброшенных секциях, невозможность `direct` для локальных inbound и реальный e2e через выбранный сервер.

**Важно про нынешние тесты:** `TestPreparePreservesRealityAndXHTTP` требует неизменности всей секции `routing`, а общая service-фикстура — профиль с `freedom`. Эти ожидания противоречат v0.2. Их нужно исправить вместе с реализацией, а не воспринимать зелёный тест как подтверждение требования. Источники: [internal/core/config_test.go:9–27](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/config_test.go#L9-L27), [internal/core/service_test.go:1–65](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/service_test.go#L1-L65).

## REVIEW-02 · P1 · Xray не зафиксирован и не проверяется по хешу

**Требования:** ADR-012, FR-07, разделы 1 и 7.

Пользователь вводит произвольный абсолютный путь. `validateBinary` проверяет только абсолютность пути и то, что это regular file. Не проверяются официальный источник, ожидаемая SHA-256 или версия Xray. В поставке прототипа движок отсутствует; README предлагает скачать его самостоятельно. Версия Xray не присутствует в `Status`/диагностике.

Источники: [internal/core/process.go:53–61](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/process.go#L53-L61), [frontend/src/App.tsx:134–139](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/frontend/src/App.tsx#L134-L139), [README.md:26–35](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/README.md#L26-L35).

**Воспроизведено:** обычный текстовый файл с именем `xray.exe` проходит `validateBinary`. Это проверка отсутствия верификации; файл не запускался и вредоносный код не использовался.

**Исправление:** закрепить release, SHA-256 именно Xray-бинарника, контролируемый путь поставки/установки и лицензионные уведомления. Проверять целостность до любого запуска, включая `run -test`, и показывать версию в UI. Проверка хеша `XrayMini.exe` не заменяет проверку Xray Core. Коммитить сам бинарник в Git необязательно: возможен воспроизводимый шаг поставки с проверкой контрольной суммы.

**Проверка:** отсутствующий/подменённый бинарник отклонён до исполнения; правильный release принимается; версия показывается; все три transport/security-комбинации проходят e2e на этой версии.

## REVIEW-03 · P1 · После аварии остаётся открытый runtime-конфиг

**Требования:** ADR-009, разделы 7–8.

Обычный cleanup реализован через `defer os.RemoveAll(tempDir)`. Но startup в `newStore` только создаёт каталог и выставляет права; старые `runtime-*` не очищаются. Документация признаёт это и предлагает ручное удаление.

Источники: [internal/core/store.go:26–39](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/store.go#L26-L39), [internal/core/service.go:152–171](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/service.go#L152-L171), [docs/ARCHITECTURE.md](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/docs/ARCHITECTURE.md).

**Воспроизведено:** после создания тестового `runtime-old-crashed-session/config.json` запуск `NewService` оставил его на месте.

**Почему это не закрывается DPAPI:** DPAPI защищает сохранённый профиль, но runtime JSON передаётся Xray открытым. Ограниченная DACL полезна и реализована, однако она не выполняет требование удалить остатки предыдущей аварийной сессии.

**Исправление:** cleanup принадлежащих завершённым/погибшим сессиям runtime-каталогов перед новыми подключениями. Для нескольких копий приложения нужна проверка владельца/живой сессии или выбранная single-instance политика. Нельзя безусловно удалять все `runtime-*`, если другая копия может работать.

**Проверка:** штатное завершение, cancel во время подготовки, авария и последующий старт; отсутствие удаления конфигурации живого экземпляра.

## REVIEW-04 · P1 · Гарантия отсутствия дочерних процессов после crash неполная

**Требования:** FR-09, ADR-006 и acceptance принудительного завершения.

В рабочем пути сначала выполняется `cmd.Start()`, затем `containProcess()`. Между этими операциями основной процесс может быть принудительно завершён, пока Xray ещё вне Job Object. Проверочный `run -test` вообще не включается в Job Object. `CommandContext` помогает при штатной отмене, но не является гарантией cleanup после смерти самого управляющего процесса.

Источники: [internal/core/process.go:31–51](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/process.go#L31-L51), [internal/core/process_windows.go:46–71](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/process_windows.go#L46-L71), [docs/ARCHITECTURE.md](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/docs/ARCHITECTURE.md).

**Статус доказательства:** выявлено чтением кода и подтверждено собственной документацией проекта; Windows crash-тест в этом ревью **не выполнялся**. Наличие KILL_ON_JOB_CLOSE — правильная основа, но оно действует на уже включённые в job процессы.

**Направление исправления:** создать процесс сразу в Job Object либо использовать эквивалентный протокол без незащищённого окна. Для Windows 10+ Microsoft описывает `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Один лишь `CREATE_SUSPENDED → AssignProcessToJobObject → ResumeThread` не устраняет окно между созданием и назначением job при crash родителя. Аналогично решить ownership проверочного процесса.

**Проверка:** принудительно завершить родителя на стадии preflight, непосредственно при создании рабочего child и после полного запуска; не оставлять ни рабочий, ни проверочный Xray. Проверить поведение вложенных jobs в реальной среде Windows.

## REVIEW-05 · P2 · Вместо согласованного single-writer используется mutex-модель

**Требования:** ADR-003, ADR-004, ADR-010; контракт событий раздела 5.

`Service` хранит один `sync.Mutex`; `Connect`, `Disconnect` и фоновая `run` меняют состояние через `publish` под этим mutex. Нет центрального Manager event loop, в который передаются команды Connect/Disconnect и типизированные worker events. Локальный `select` в `run` обрабатывает завершение, отмену и health, но это не согласованный командный event loop.

`session.id` равен ID профиля, а не уникальному ID подключения. При этом защита от старых сессий **частично и фактически реализована иначе**: сравнивается указатель `s.active == run`, каналы принадлежат экземпляру сессии, а новая сессия не допускается до cleanup. Поэтому отсутствие отдельного sessionID не доказывает ошибку изоляции в текущем коде.

`publish` создаёт `go callback(status)` на каждое обновление, без собственной ограниченной очереди и ожидания завершения callback-задач. `ListProfiles`, `ImportProfile`, `DeleteProfile` держат тот же mutex во время файлового I/O и DPAPI; `Connect` — во время `os.Stat`. Значит, медленное хранилище потенциально задержит GetStatus/Disconnect. Это структурный риск, не воспроизведённое зависание.

Источник: [internal/core/service.go:24–150](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/service.go#L24-L150).

**Оценка:** в прогнанных исходных тестах race detector не нашёл гонок. Mutex — допустимый архитектурный подход, но **не тот ADR, который принят в v0.2**.

**Исправление по текущей спеке:** единый владелец состояния, неблокирующий event loop, уникальный sessionID, события с идентификатором, I/O вне цикла, ограниченная доставка уведомлений. Альтернатива — отдельное согласованное изменение ADR и доказательство эквивалентных гарантий; текущая документация реализации сама по себе не пересматривает исходные требования.

## REVIEW-06 · P2 · Политика health-check отличается от спецификации

**Требования:** FR-06, ADR-007, модель статуса раздела 5.

Спека задаёт timeout 5 секунд, периодические проверки без перекрытия, Degraded после двух последовательных неудачных проверок и возврат в Connected после успеха.

Реализация использует `http.Client.Timeout = 8s`; внутри каждого цикла делает до трёх попыток с паузами 500 ms, публикует общий bool и только после этого ждёт 30 секунд. Это **не счётчик двух последовательных периодических проверок**. В UI есть running/unhealthy, но нет предусмотренной политики Degraded. Нет времени последней проверки в Status.

Источники: [internal/core/process.go:79–93](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/process.go#L79-L93), [internal/core/service.go:219–280](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/service.go#L219-L280), [frontend/src/App.tsx:22–23](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/frontend/src/App.tsx#L22-L23).

**Что уже хорошо:** запрос действительно сконфигурирован через локальный HTTP-прокси; положительный статус не выставляется просто по PID; проверки последовательны; отмена привязана к сессии; автоперезапуска нет. Работа SOCKS5 реальным запросом здесь не проверяется; его проверка нужна при приёмке.

**Исправление:** отделить первоначальное ожидание готовности от периодических probes; в периодической политике одна проверка с timeout 5s, явный счётчик failures, Degraded после двух и сброс после успеха; хранить lastCheckedAt. Не обещать, что один контрольный сайт доказывает работоспособность всех назначений.

**Проверка:** success → failure → failure → success; состояние и timestamps на каждом шаге; остановка во время probe; отсутствие перекрытия и direct-обхода тестового трафика.

## REVIEW-07 · P2 · Диагностика не читает Xray, версия не отображается

**Требования:** FR-07, ADR-005/010, компоненты Log Readers.

Runtime задаёт `loglevel: none`, а stdout/stderr процесса оставлены nil, то есть вывод отправляется в null device. `GetLogs` отдаёт до 200 сообщений о переходах состояния, а не очищенные диагностические записи Xray. Все записи имеют уровень info. В конкретной реализации отсутствуют Log Readers и сведения о версии движка.

Источники: [internal/core/config.go:41–43](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/config.go#L41-L43), [internal/core/process.go:31–51](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/process.go#L31-L51), [internal/core/service.go:81–98](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/service.go#L81-L98).

**Оценка:** отключение сырых логов снижает риск утечки секретов, но не реализует согласованную модель диагностики. Это не deadlock из-за непрочитанных pipes: pipes здесь не создаются.

**Исправление:** ограниченная диагностика, безопасные уровни/категории ошибок и версия; при включении вывода Xray — дренирование stdout/stderr, ограничение длины строк/буфера, редактирование секретов и контроль остановки readers. Не включать raw logging без фильтрации ради формального выполнения требования.

## REVIEW-08 · P2 · Неполный контракт профилей и UI API

**Требования:** FR-01, FR-08, ADR-008, раздел 5.

`RenameProfile` отсутствует в backend и UI. Вместо `GetRecentLogs(limit)` — `GetLogs()` без параметра. `Connect` принимает дополнительные `xrayPath` и возвращает snapshot. Backend публикует событие `status`, а не `connection:state-changed`; frontend вообще не подписывается на него и опрашивает backend каждые 1,5 секунды.

Источники: [app.go:55–96](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/app.go#L55-L96), [frontend/src/bridge.ts:5–26](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/frontend/src/bridge.ts#L5-L26), [frontend/src/App.tsx:48–68](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/frontend/src/App.tsx#L48-L68).

**Что соответствует смыслу ADR-008:** источник истины остаётся backend; начальный GetStatus есть; UI отбрасывает старую revision. Поэтому polling — осознанная альтернатива доставки, а не автоматически некорректное управление состоянием. Но событие, API и rename не соответствуют указанному контракту.

**Исправление:** реализовать rename, согласованный API логов и event + snapshot восстановления, либо отдельно утвердить изменения необязательных деталей API. Смена названий папок не является замечанием: спецификация допускает свою структуру кода.

## REVIEW-09 · Приёмочный пробел · Нет подтверждения обязательных платформы и транспортов

**Требования:** раздел 8 и ADR-012.

Сохранение JSON-ветки REALITY/XHTTP не доказывает успешное подключение. В тестах `processRunner` и `probe` в основном заменены fakes; отдельный реальный дочерний процесс — тестовый helper, а не Xray Core. Документ VERIFICATION прямо говорит, что Windows runtime, DPAPI/DACL/Job Object и real Xray/network e2e не запускались.

Источники: [internal/core/service_test.go](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/service_test.go), [internal/core/process_test.go](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/internal/core/process_test.go), [docs/VERIFICATION.md:35–54](https://github.com/slonikmak/XRay-mini/blob/50b8cb36b311148871d21084c0b83dfba51198ed/docs/VERIFICATION.md#L35-L54).

**Не следует заключать:** «XHTTP+TLS не работает» или «сборка точно не запускается». Верный статус — **не подтверждено**.

**Чтобы закрыть приёмку:** фактический запуск на Windows 10/11 без администратора, проверка WebView2; отдельные подключения RAW+REALITY, XHTTP+REALITY, XHTTP+TLS; HTTP и SOCKS5; принудительное завершение родителя; права/DPAPI; отключение и восстановление сети; порты; crash-recovery файлов. Подпись, auto-update и TUN не требуются для этого MVP и не включены в список нарушений.

## Покрытие функциональных требований

- **FR-01 — частично.** Импорт, список, выбор и удаление есть; переименование отсутствует. Одновременная активная сессия ограничена в одном экземпляре Service.
- **FR-02 — не выполнено.** Не проверяются один VLESS и streamSettings; лишние маршруты/выходы сохраняются; нет согласованного preview отброшенных секций.
- **FR-03 — частично.** Временный JSON и Xray preflight есть; собственная явная VLESS-маршрутизация отсутствует.
- **FR-04 — частично.** Два фиксированных loopback-inbound и проверка конфликтов есть; отсутствие direct-обхода не обеспечено.
- **FR-05 — в основном реализовано по поведению.** Connect/Disconnect/GetStatus, guard двойного запуска, cancel и ожидание cleanup есть; архитектурный контракт событий другой. Процессные Windows-гонки ещё требуют проверки.
- **FR-06 — частично.** HTTP probe и его отмена есть; timeout/порог деградации и связанные состояния отличаются.
- **FR-07 — частично.** Безопасные общие ошибки и ограниченный журнал переходов есть; версии Xray и согласованной runtime-диагностики нет.
- **FR-08 — реализован основной UI.** Профили, кнопки, отдельные состояния, адреса и журнал присутствуют; Windows runtime/визуальная приёмка не подтверждены. Файловые операции под общим mutex дают риск задержки команд.
- **FR-09 — частично.** Штатное завершение и удаление runtime есть; crash-гарантии неполны, стартовая очистка остатков отсутствует.

## Покрытие Architecture Decision Rules

- **ADR-001 — реализовано по коду:** отдельный Xray child, движок не встроен.
- **ADR-002 — реализовано по коду:** один Go backend, Wails bindings, без своего HTTP API/микросервисов.
- **ADR-003 — отклонение:** mutex-сервис вместо single-writer event loop.
- **ADR-004 — частично/иная реализация:** context и ownership есть; уникального sessionID и событий по контракту нет, используется identity указателя сессии.
- **ADR-005 — основное владение процессом реализовано:** один Wait по каждому успешному пути; сырые логи не собираются, а отбрасываются.
- **ADR-006 — частично:** Job Object/KILL_ON_JOB_CLOSE есть, но назначается после запуска; preflight вне job; crash-тест не выполнен.
- **ADR-007 — частично:** process/network разделены, но правило двух неудачных проверок не реализовано.
- **ADR-008 — частично:** backend и revision — источник истины; вместо согласованной event-подписки frontend polling.
- **ADR-009 — частично:** DPAPI/DACL и нормальный cleanup есть; runtime-исполнение Windows не проверено, startup recovery отсутствует.
- **ADR-010 — частично:** проверки не перекрываются и журнал ограничен; нет manager loop и readers, callback-goroutines не ограничены/не отслеживаются.
- **ADR-011 — реализовано по коду:** TUN, настройка системного proxy и маршрутов отсутствуют; область действия — только настроенные приложения.
- **ADR-012 — не выполнено:** произвольный путь Xray без pinned release/hash, три e2e не подтверждены.

## Рекомендуемый порядок исправлений

Сначала REVIEW-01 — контракт импорта и принудительный VLESS-маршрут: сейчас это самое существенное расхождение обещанного поведения и конфигурации. Затем REVIEW-02/03/04 — доверенный движок, recovery секретов и crash-safe ownership. После этого привести manager, health policy и UI/API к ADR либо явно пересмотреть конкретные решения в спецификации. Завершить Windows и network e2e; зелёные unit-тесты не заменяют эти этапы.

## Приложенные дополнительные тесты

`review_spec_v02_test.go` содержит пять функций / семь сценариев:

1. Отклонение конфигурации без VLESS.
2. Отклонение неоднозначного выбора двух VLESS.
3. Отклонение VLESS без streamSettings.
4. Исключение direct outbound и исходного direct routing из runtime.
5. Создание явного runtime routing.
6. Очистка orphan runtime-конфига при старте.
7. Отклонение непроверенного произвольного файла вместо Xray.

Они предназначены как начальные regression-проверки, не как полная приёмочная suite. Проверка executable не исполняет указанный файл. Cleanup-тест использует только собственный `t.TempDir`; будущую политику нескольких экземпляров нужно покрыть отдельно. После исправления контракта следует обновить и старые тестовые фикстуры.
