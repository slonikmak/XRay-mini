# Архитектура

## Границы

React/TypeScript отвечает за интерфейс и вызывает Wails bindings. `App` в корне проекта — тонкий Wails v3 service, зарегистрированный через `application.NewService`. `ServiceStartup` открывает локальное хранилище до готовности UI; `ServiceShutdown` закрывает сервис и останавливает процесс. Runtime и сгенерированные bindings закреплены на v3.0.0. `internal/core` отвечает за профили, конфигурацию, жизненный цикл Xray и сетевую проверку. Отдельный `xray.exe` реализует VLESS/REALITY/XHTTP. Собственный HTTP-сервер, демон и микросервисы не нужны.

## Параллельная работа

Интерфейс не ждёт завершения всего подключения. Connect резервирует сессию и возвращает состояние; подготовка и последующие проверки идут в фоне. Disconnect отменяет сессию, а остановка и очистка завершаются асинхронно. Пока прежняя сессия не очищена, повторный запуск не допускается. Снимок состояния доступен через GetStatus; интерфейс опрашивает его раз в 1,5 секунды. Адаптер также публикует типизированное событие `status` через v3 `app.Event.Emit` для будущих подписчиков. UI продолжает использовать проверенный polling; v2 `window.go` не используется. Монотонная revision не позволяет старому снимку заменить более новый.

Процесс ожидается ровно один раз. Фоновые события относятся к конкретной сессии; устаревшая проверка не должна изменять новую сессию. Жизненный цикл процесса и доступность сети представлены отдельно. Закрытие приложения останавливает активную сессию.

## Хранение и доверие

Профили находятся в пользовательском каталоге конфигурации `XrayMini`. Windows DPAPI привязывает зашифрованный профиль к текущему пользователю. Исполняемый Xray получает временный открытый JSON, который удаляется после завершения сессии. Это не защита от администратора, скомпрометированного текущего пользователя или вредоносного исполняемого файла.

Raw-вывод Xray не показывается: конфигурации и внешние диагностические сообщения могут содержать UUID, адреса и другие секреты. Поэтому ошибки проверки намеренно общие; для глубокой диагностики используйте доверенные инструменты самостоятельно и не публикуйте конфиги с секретами.

## Не реализовано

TUN, kill switch, системная маршрутизация, автопереключение прокси, подписки, импорт ссылок, автообновления, несколько одновременных подключений, автоматическое восстановление соединения. В первой версии фиксированы порты и адрес health-check. Нужна отдельная реальная проверка на Windows и с вашим сервером.

## Ограничения завершения и Windows

Для основного процесса используется Windows Job Object с `KILL_ON_JOB_CLOSE`. Присоединение происходит сразу **после** запуска процесса, а не через suspended-create: остаётся небольшое окно до присоединения. Preflight-процесс `run -test` завершается через отмену `CommandContext` и не помещается в Job Object. Это приемлемо только для доверенного Xray; механизм не является песочницей для неизвестных exe.

После аварии ОС/приложения временный открытый конфиг может остаться в `XrayMini/runtime-*`. Каталог на Windows ограничен DACL текущего пользователя и SYSTEM; при нормальном отключении файлы удаляются. Автоматической зачистки старых runtime-каталогов нет, чтобы не удалить данные другой работающей копии. При необходимости удаляйте их вручную после закрытия всех экземпляров.

Параллельный запуск нескольких экземпляров не блокируется глобальным mutex. Фиксированные порты проверяются перед запуском, но между проверкой и запуском есть обычное окно гонки за порт. Внешний Xray должен завершиться при конфликте; это отображается как ошибка. Проверки не заменяют проверку реального бинарника на целевой ОС.
