# Xray Mini — MVP Specification & Architecture Decision Rules

**Версия:** 0.2  
**Статус:** проект спецификации  
**Платформа:** Windows 10/11, x64  
**Тип продукта:** локальный proxy-клиент (не системный VPN)

## 1. Назначение и границы MVP

Xray Mini — небольшое Windows-приложение, позволяющее импортировать клиентскую конфигурацию Xray, выбрать профиль и направить трафик приложений через локальный SOCKS5/HTTP-прокси.

Весь проксируемый трафик обрабатывает **официальный Xray-core**. Собственное приложение отвечает только за профили, запуск и контроль процесса Xray, проверки доступности и UI.

**Обязательные комбинации:**
- VLESS + RAW + REALITY;
- VLESS + XHTTP + REALITY;
- VLESS + XHTTP + TLS.

**Стек:** Go + Wails 3, React + TypeScript, поставляемый отдельно `xray.exe`. Для Windows UI используется WebView2. Версии Wails и Xray фиксируются на проверенных сборках; разработка Wails 3 требует Go 1.26+.

**Не входит:** TUN, маршрутизация всего трафика Windows, системные proxy-настройки, kill switch, split tunneling, автоподписки, редактирование произвольных параметров Xray, автообновление, автостарт с Windows, серверная часть и собственная криптография.

## 2. Функциональные требования

**FR-01 — Профили.** Добавление через импорт Xray JSON, список сохранённых профилей, выбор, переименование и удаление. Одновременно активен не более одного профиля. Конфигурации хранятся локально.

**FR-02 — Контракт импорта.** MVP принимает клиентский JSON, содержащий **ровно один целевой VLESS outbound** с `streamSettings`. Если файл содержит дополнительные `inbounds`, `routing` или иные outbounds, они не переносятся молча: перед импортом показывается, что будет использован только целевой VLESS outbound; неподдерживаемая неоднозначность — ошибка импорта. RAW/REALITY и XHTTP/REALITY/TLS передаются в Xray без собственной реализации протоколов. Исходный файл не изменяется.

**FR-03 — Runtime-конфигурация.** Go создаёт отдельный runtime JSON: выбранный VLESS outbound, явно заданная маршрутизация локального прокси через него и два локальных inbound. Runtime-конфигурация проверяется через `xray run -test -c <file>`; проверка синтаксиса **не означает** доступности сервера.

**FR-04 — Локальные прокси.** SOCKS5 на `127.0.0.1:10808`, HTTP proxy на `127.0.0.1:10809`. Оба порта проверяются на конфликты. Нельзя слушать `0.0.0.0`, внешний интерфейс или автоматически менять настройки Windows. Весь трафик этих двух inbound направляется через выбранный VLESS outbound, без неявного обхода через direct.

**FR-05 — Управление сессией.** Connect, Disconnect, GetStatus. Connect не запускает второй процесс при активной или запускающейся сессии. Disconnect во время Connecting отменяет запуск и освобождает ресурсы. Смена профиля выполняется только после завершения предыдущей сессии.

**FR-06 — Проверка подключения.** После запуска Xray приложение проверяет доступность локального прокси и выполнение настоящего HTTP-запроса **через** него. `Connected` означает успешную последнюю end-to-end проверку, а не постоянный VPN-туннель. Периодическая проверка выполняется без перекрывающихся запросов и с таймаутом (для MVP: интервал 30 секунд, timeout одного запроса 5 секунд). Ошибка одной проверки не обязана завершать Xray; деградация отображается отдельно.

**FR-07 — Диагностика.** Текущее состояние, безопасные сообщения об ошибках, версия Xray, последние записи логов. Буфер ограничен по размеру; секреты конфигурации и URL с секретными параметрами не логируются.

**FR-08 — Интерфейс.** Одно окно: список профилей, импорт/удаление, выбор, Connect/Disconnect, статусы, адреса SOCKS5/HTTP и диагностическая панель. UI отзывчив при операциях с сетью и дочерним процессом.

**FR-09 — Завершение.** При штатном выходе, ошибке запуска и отмене сессии приложение останавливает принадлежащий ему Xray и освобождает временные файлы/ресурсы. Аварийное завершение основного приложения не должно оставлять работающий Xray-процесс.

## 3. Процессы и компоненты

```text
xray-mini.exe (один Go-процесс + Wails)
├─ Wails Service / API     ↔ React/TypeScript UI (WebView2)
├─ Profile Repository      (локальное хранение)
├─ Connection Manager      (единственный владелец состояния)
│  ├─ Startup Task         (проверка конфига, запуск)
│  ├─ Process Supervisor   (владение child process, Wait, остановка)
│  ├─ Health Checker       (периодические запросы через proxy)
│  └─ Log Readers          (stdout/stderr → bounded log buffer)
└─ Diagnostics / Event Publisher
          │ os/exec + Windows Job Object
          ▼
xray.exe (отдельный дочерний процесс)
├─ SOCKS5 127.0.0.1:10808
├─ HTTP   127.0.0.1:10809
└─ VLESS → REALITY / XHTTP / TLS → удалённый сервер
```

**Важно:** Startup Task, Health Checker, Process Supervisor и Log Readers — логические роли/горутины, **не отдельные Windows-процессы**. В обычном режиме есть основной процесс приложения и один рабочий `xray.exe`; для `-test` временно запускается кратковременный проверочный процесс. WebView2 может создавать собственные служебные процессы. Пользовательский трафик **не проходит** через Go и React.

## 4. Architecture Decision Rules (ADR)

### ADR-001 — Xray-core как отдельный процесс

**Решение:** использовать поставляемый `xray.exe`, не встраивать движок как библиотеку и не реализовывать VLESS/REALITY/XHTTP самостоятельно.  
**Причина:** изоляция ошибок, более простой жизненный цикл и независимое тестирование.  
**Следствие:** нужны Process Supervisor, проверка версии/целостности бинарника и корректная остановка.

### ADR-002 — Один Go-бэкенд, никаких микросервисов

**Решение:** вся прикладная логика живёт внутри процесса Wails. Wails service bindings — команды из UI, Wails events — уведомления в UI; отдельный HTTP-сервер для приложения не нужен.  
**Причина:** небольшой локальный MVP, без лишнего IPC и инфраструктуры.

### ADR-003 — Single writer для состояния подключения

**Решение:** `ConnectionManager` последовательно обрабатывает команды и события через event loop (`channels` + `select`). Только он изменяет состояние сессии. Фоновые задачи **отправляют события**, но не меняют общий `status`.  
**Причина:** избежать гонок между Connect, Disconnect, падением Xray и результатами health checks.  
**Следствие:** длительные операции не должны блокировать event loop; GetStatus получает согласованный snapshot.

### ADR-004 — Ресурсы принадлежат сессии

**Решение:** при Connect создаются `sessionID` и `context.Context`. Worker events содержат `sessionID`; устаревшие результаты не меняют новую сессию. Отмена контекста останавливает фоновые проверки, но сама по себе не считается подтверждением остановки `xray.exe`.  
**Причина:** корректно обрабатывать Disconnect во время Connecting и поздние результаты.  
**Следствие:** запущенный процесс регистрируется у Supervisor **до** публикации `ProcessStarted`; если запуск завершился после отмены, процесс всё равно должен быть остановлен и дождаться `Wait`.

### ADR-005 — Один Process Supervisor на рабочий Xray

**Решение:** Supervisor является единственным владельцем handle процесса и результата `cmd.Wait()`. `Wait` вызывается ровно один раз. Завершение `xray.exe` публикуется как `ProcessExited`. Stdout/stderr дренируются, чтобы вывод дочернего процесса не блокировал работу.  
**Причина:** предсказуемое завершение, отсутствие double-Wait и утечек ресурсов.

### ADR-006 — Windows Job Object для контроля дочернего процесса

**Решение:** рабочий Xray привязывается к Windows Job Object с политикой `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. При штатном Disconnect Supervisor завершает процесс и дожидается выхода; при аварийном завершении приложения Job Object обеспечивает cleanup.  
**Причина:** не оставлять работающий прокси после падения управляющего приложения.  
**Следствие:** нужен Windows-specific адаптер и тест аварийного завершения на реальной Windows.

### ADR-007 — Разделять ProcessState и NetworkHealth

**Решение:** живой PID и открытый порт не означают установленное соединение. Отдельно храним жизненный цикл процесса и результат последнего запроса через прокси. При двух последовательных неудачных проверках показывается `Degraded`, при успешной последующей проверке — `Connected`; процесс автоматически не перезапускается.  
**Причина:** не путать недоступность тестового ресурса, сервера и смерть Xray.

### ADR-008 — UI не является источником истины

**Решение:** React вызывает `Connect`, `Disconnect`, `GetStatus` и получает `connection:state-changed`. Методы подключения подтверждают принятие команды, а не завершение подключения. При создании окна UI всегда запрашивает свежий `GetStatus`; события могут быть пропущены.  
**Причина:** предсказуемое восстановление UI и отсутствие независимого состояния соединения во frontend.

### ADR-009 — Изоляция профилей и секретов

**Решение:** Profile Repository хранит чувствительные поля с защитой средствами Windows DPAPI. Runtime JSON создаётся отдельно на время сессии, с доступом только текущего пользователя, и удаляется после завершения. Остатки временных конфигураций предыдущего аварийного запуска очищаются при старте.  
**Причина:** минимизация хранения открытых ключей доступа и секретов.  
**Ограничение:** кратковременный runtime JSON содержит параметры подключения в открытом виде; очистка после аварии не равна гарантированному безопасному уничтожению данных с диска.

### ADR-010 — Ограниченные фоновые задачи, без worker pool

**Решение:** одна event-loop goroutine менеджера; по одной задаче ожидания Xray и periodic health check на активную сессию; ограниченное число читателей логов. Логи поступают в bounded ring buffer. Проверки не перекрываются; `context`/timeouts управляют отменой.  
**Причина:** небольшое фиксированное число задач, понятные lifecycle и backpressure.

### ADR-011 — Локальный proxy, а не системный VPN

**Решение:** приложение не перехватывает весь трафик Windows. Только программы, настроенные на `127.0.0.1:10808/10809`, пользуются Xray. При остановке прокси их трафик больше не проходит через него; поведение приложений с fallback вне нашего контроля.  
**Причина:** MVP без драйверов, маршрутизации, прав администратора и kill switch.

### ADR-012 — Проверяемая совместимость Xray

**Решение:** зафиксировать конкретный проверенный release Xray и контрольную сумму поставляемого бинарника. Проводить отдельные интеграционные проверки всех трёх обязательных комбинаций.  
**Причина:** схема конфигурации и поведение транспорта могут меняться между выпусками.

## 5. Контракт управления и модель состояния

**Команды Wails API:** `ListProfiles()`, `ImportProfile(json)`, `RenameProfile(id, name)`, `DeleteProfile(id)`, `Connect(profileID)`, `Disconnect()`, `GetStatus()`, `GetRecentLogs(limit)`. Секретные поля сохранённого профиля не возвращаются в UI через `ListProfiles` и `GetStatus`.

**События Manager:** `ConfigValidated`, `ProcessStarted`, `ProcessExited`, `ProxyReady`, `HealthFailed`, `StopCompleted`. Каждое асинхронное событие содержит `sessionID`; события статуса в UI содержат ещё и монотонный `revision`.

**Отображаемые состояния:** `Disconnected`, `Connecting`, `Connected`, `Degraded`, `Disconnecting`, `Error`. Подробный статус также включает `processState`, `networkHealth`, ID активного профиля, безопасное сообщение об ошибке и время проверки.

```text
Disconnected --Connect--> Connecting --успешный proxy probe--> Connected
                              │                                  │   ▲
                              │ ошибка                           │   │
                              ▼                                  ▼   │
                            Error                            Degraded
                              │                        (проверка неуспешна /
                              │                         снова успешна)
                              └-- Connect после cleanup --> Connecting

Connecting / Connected / Degraded --Disconnect--> Disconnecting
                                                    │ cleanup завершён
                                                    ▼
                                                Disconnected
```

`Error` — видимое состояние ошибки **после очистки ресурсов**; повторный Connect допустим только после завершённого cleanup. Disconnect допустим и во время Connecting. `Connected` не означает постоянно активный туннель к серверу.

## 6. Сценарий Connect / Disconnect

**Connect:** UI отправляет `Connect(profileID)` → Manager отклоняет дубликат, создаёт сессию и публикует `Connecting` → Startup Task готовит runtime JSON и выполняет `xray run -test -c` → Supervisor запускает рабочий Xray и регистрирует владение процессом → запускаются логирование и Health Checker → успешный запрос через proxy создаёт `ProxyReady` → Manager публикует `Connected`.

**Disconnect:** Manager переводит сессию в `Disconnecting` → отменяет фоновые проверки → Supervisor завершает Xray и дожидается единственного `Wait` → освобождаются порты, временный config и ресурсы → Manager публикует `Disconnected`.

**Ошибки:** невалидный JSON, занятые порты, отсутствие бинарника, выход Xray, timeout или отмена — отдельные причины, видимые в диагностике. Менеджер не делает автоматический restart-loop. Поздние события старой сессии не влияют на актуальную; её ресурсы всё равно завершаются.

## 7. Нефункциональные требования

- **Windows:** Windows 10/11 x64, без прав администратора. Наличие WebView2 проверяется или обеспечивается способом поставки; приложение не устанавливает системные драйверы. Поставка Xray сопровождается необходимыми лицензионными уведомлениями.
- **UI:** длительные операции никогда не блокируют UI; Connect возвращает управление сразу после принятия команды.
- **Надёжность:** нельзя одновременно запустить два рабочих Xray; завершённая сессия не оставляет goroutines, файлов или дочернего процесса.
- **Защита:** прокси доступны только на loopback, секреты не включаются в логи, runtime-конфиг ограничен ACL текущего пользователя, поставляемый Xray проверяется по хешу.
- **Диагностика:** ошибки разделяются на ошибки конфигурации, процесса и сети; логи ограничены и очищаются от секретных данных.
- **Проверки:** Health Checker использует таймаут, не допускает перекрывающихся запросов и не выполняет бесконечные быстрые повторы. При недоступном контрольном ресурсе сообщает ограниченность диагностики, не объявляя автоматически виноватым сервер.

## 8. Acceptance Criteria и проверочные сценарии

**Рабочие сценарии:**
- Импортируется валидный JSON с VLESS; невалидный/неоднозначный профиль отклоняется с объяснением.
- Каждый из трёх требуемых транспортов подключается к соответствующему тестовому серверу; проверка идёт через локальный SOCKS5/HTTP.
- На Windows 10/11 x64 приложение запускается без администратора и корректно обрабатывает отсутствие WebView2.
- Два localhost proxy слушают только `127.0.0.1`; запросы не обходят выбранный Xray outbound.
- Connect показывает `Connecting`, затем `Connected` **только после** успешной сетевой проверки.

**Конкурентность и отказы:**
- Двойной Connect не создаёт второй Xray.
- Disconnect во время проверки config и во время запуска child process завершает обе операции без оставшегося процесса.
- Запоздалый `HealthResult`/`ProcessStarted` от старой сессии не изменяет текущую сессию.
- Падение Xray обнаруживается через `Wait`, UI получает корректное состояние; двойного `Wait` нет.
- Потеря сети меняет состояние на `Degraded`, восстановление возвращает `Connected`; автоматический перезапуск не происходит.
- Занятый localhost-порт приводит к ясной ошибке и полной очистке сессии.
- После обычного Disconnect и после принудительного завершения `xray-mini.exe` не остаётся рабочего `xray.exe`.
- После закрытия окна и повторного открытия состояние восстанавливается из Go `GetStatus`, без зависимости от сохранённого состояния React.
- Секретные значения не обнаруживаются в логах; оставшиеся временные config-файлы выявляются и удаляются при следующем старте.

**Уровни проверок:** unit — state machine/manager/config/profile; integration — реальный `xray.exe` и proxy health; Windows system tests — Job Object, WebView2, package, процессные гонки; network e2e — три комбинации на тестовых серверах. Наличие теста само по себе не считается успешной приёмкой: требуется фактический проход.

## 9. Структура компонентов (ориентир)

```text
backend/
  app/          Wails service, публикация UI events
  connection/   Manager, session, commands, events, state
  xray/         config builder/validator, process supervisor
  health/       proxy probe
  profiles/     encrypted repository
  diagnostics/  bounded log collector
  windows/      Job Object, secure storage adapter
frontend/
  features/profiles/
  features/connection/
  features/diagnostics/
```

Папки — ориентировочная декомпозиция, а не требование к конкретным именам файлов. Обязательны **границы ответственности**: UI не вызывает Xray/Windows напрямую; Go Wails service не содержит протокольную реализацию; менеджер не выполняет длительный I/O внутри event loop.
