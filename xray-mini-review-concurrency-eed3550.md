# Xray Mini — ревью обновлений и concurrency

**Дата:** 1 ноября 2026 года.  
**Проверенный commit:** `eed355017638e1834a957808438148cff1a011eb` (`main` на начало проверки).  
**Предыдущая база:** `910c353955f02b071fb545b0512b7585cca85189`.  
**Основание:** исходная спецификация v0.2, текущий исходный код, текущие документы приёмки и локальные регрессионные проверки. Репозиторий не изменялся.

## Вердикт

**Основная concurrency-архитектура соответствует тому, что планировали:** один управляющий Go-процесс, внешний Xray, single-writer event loop, отдельный worker сессии, один Wait, последовательный health checker, ограниченные уведомления и дренирование вывода. Это не набор несвязанных goroutines.

**Полной корректности конкурентного поведения пока нет.** Подтверждены два дефекта/пробела сценариев жизненного цикла: поздний успешный health после ProcessExited и отсутствие повторной попытки остановки после ошибки Kill. В интерфейсе осталось прежнее связывание профильных операций и Disconnect общей блокировкой. Два первых сценария воспроизведены детерминированными unit-тестами; UI-замечание основано на чтении текущего кода.

39 существующих top-level тестов выбранной подсистемы прошли дважды с race detector. Это положительный результат для проверенных путей, но не доказательство отсутствия ошибок порядка событий, зависаний при отказах или проблем на Windows.

Через GitHub-коннектор прочитаны актуальные `service.go`, `process.go`, `process_windows.go`, `runtime.go`, `app.go`, `subscription.go`, `frontend/src/App.tsx`, документы архитектуры, verification, scope и отдельный отчёт внешнего подключения.

Они скопированы без изменения в минимальный модуль, поскольку окружение содержит Go 1.23.2/Linux, а проект требует Go 1.26.10. Manifest со списком файлов и хешами приложен.

## R3-01 — P2. ProcessExited не запрещает поздний Connected

**Состояние:** прежнее замечание повторного ревью остаётся открытым.

**Код:** `internal/core/service.go:414–424`, `509–514`, `573–585`.

В Manager обработчик `ProcessExited` содержит только комментарий. Факт завершения процесса не меняет внутреннюю фазу и не запрещает принимать `ProcessStarted`, `ProxyReady` или `HealthFailed` этой же сессии.

Поток ожидания выполняет:

```go
err := child.Wait()
s.event(run, "ProcessExited", "", false)
exited <- err
```

В это же время session worker может получить результат уже завершившейся проверки. Между публикацией ProcessExited и отправкой во внутренний канал exited возможно переключение goroutine. Проверка внутреннего канала тогда ещё ничего не увидит, а ProxyReady попадёт в очередь событий после ProcessExited.

```text
ProcessExited
    → Manager ничего не фиксирует
    → запоздалый ProxyReady той же сессии
    → Connected / running / healthy
    → позднее StopCompleted исправит состояние
```

**Почему sessionID не помогает:** события относятся к одной и той же сессии. Защита от событий предыдущей сессии работает, но это другая гарантия. Нужна также монотонность стадии внутри сессии.

**Воспроизведение:** `TestReviewR3ExitedSessionRejectsLateSuccessfulHealth` направляет Manager упорядоченную пару событий ProcessExited → ProxyReady. Ошибка воспроизвелась **5/5**:

```text
late health resurrects an exited session before cleanup:
state=Connected process=running health=healthy
```

Это manager-level тест допустимого порядка событий, НЕ Windows/e2e-тест падения Xray. Он не измеряет частоту такого чередования в эксплуатации.

**Исправление:** при ProcessExited фиксировать терминальную фазу процесса и запрещать рабочие/health-переходы до окончания этой сессии. StopCompleted по-прежнему должен быть единственным разрешением на новый Connect. Не подменять «cleanup ещё идёт» утверждением «Xray ещё работает». Сохранить причину неожиданного выхода до финального состояния.

**Недостающий регрессионный набор:** ProcessExited → ProxyReady; ProcessExited → ProcessStarted; ProcessExited → HealthFailed; Disconnect → поздний успех; события предыдущей сессии после нового Connect.

## R3-02 — P2. После неуспешного Kill нет явного восстановления остановки

**Состояние:** обнаруженный пробел обработки отказа, не гонка доступа к памяти.

**Код:** `internal/core/service.go:342–346`, `360–365`, `560–565`; `internal/core/process_windows.go:73–87`.

Session worker при отмене делает один Kill. Если он вернул ошибку, публикует StopFailed, но затем безусловно ждёт `<-exited`:

```go
if err := child.Kill(); err != nil {
    s.event(run, "StopFailed", "", false)
}
<-exited
```

Новый Disconnect или Close снова вызывает уже выполненный cancel. Канал `retryCleanup` относится только к удалению runtime-файлов. Повторного управляющего сигнала для остановки процесса нет. Если процесс сам не завершится, worker остаётся ждать; новый Connect правильно запрещён, но пользователь не получает способ повторить остановку внутри приложения.

**Важно:** нативный Windows-адаптер дополнительно делает собственную однократную попытку Kill при отмене context. Это может помочь на первом этапе, но не даёт повторной попытки на последующую явную команду пользователя. Рассматриваемый отказ — начальные попытки не завершили процесс.

**Воспроизведение:** fake child возвращает ошибку на первый Kill, а на второй завершился бы успешно. После второго Disconnect счётчик остаётся равным 1, Wait вызывается один раз, статус становится Disconnecting/stopping и больше не завершается. **5/5**. Тест освобождает fake child при cleanup и не создаёт сиротский настоящий процесс.

**Что сделано правильно:** процесс и lock не объявляются свободными преждевременно; новый экземпляр не запускается поверх старого. Это нужно сохранить.

**Исправление:** добавить управляемую явную команду RetryStop/повторный Disconnect в Supervisor. Одна попытка на явный запрос, с проверяемым результатом и сохранением единственного Wait. Не вводить автоматический restart-loop или бесконечный повтор по уже закрытому `ctx.Done()`. Если операция намеренно невосстановима в рамках текущего процесса, это должно быть отражено в UI с понятной инструкцией, а не бесконечным Stopping.

## R3-03 — P2. Профильная операция по-прежнему блокирует Disconnect

**Состояние:** прежнее UI-замечание остаётся открытым; вывод по исходникам, не новый frontend-прогон.

**Код:** `frontend/src/App.tsx`: `perform`, `closeModal`, `toggleConnection`, `Modal`, условия disabled кнопки соединения.

Все мутации по-прежнему проходят через общий `lock.current`/`busy`. Во время импорта, переименования или удаления нельзя отправить Disconnect. Открытый dialog также нельзя закрыть, пока `busy` установлен. Профильные операции доступны при работающем соединении.

```text
Connected
    → Rename/Import
    → задержка сохранения/DPAPI
    → busy=true; dialog нельзя закрыть; Disconnect недоступен
```

Manager при этом остаётся отзывчивым: проблема в том, что UI не отправляет команду. Исправление предыдущего случая «после Connect завис refresh профилей» полезно, но не решает блокировку во время самой профильной мутации.

**Исправление:** независимые блокировки connection commands и profile mutations плюс доступный путь Stop. Одного разделения `busy` мало, если модальный dialog делает фон недоступным. Более простой вариант для MVP — запрет профильных мутаций при активной/запускающейся сессии.

**Нужный UI-тест:** подключение активно → Promise RenameProfile/ImportProfile удерживается незавершённым → пользователь может инициировать Disconnect, либо профильную операцию нельзя было начать. Backend Disconnect должен быть вызван до завершения сохранения.

## Дополнительные замечания, не равнозначные основным дефектам

### Late bridge injection: подписка не восстанавливается автоматически

В App.tsx `SubscribeStatus` вызывается внутри effect с зависимостью только от стабильного `refresh`. Если `desktop()` был недоступен именно при первом выполнении effect, подписка не создаётся. Поздний refresh на focus способен показать bridge как available, но не повторяет подписку. Это условный сценарий: нет утверждения, что нативный Wails обязательно запускается в таком порядке. Однако документация отдельно заявляет поддержку позднего появления host. Стоит добавить тест «bridge отсутствовал → появился → затем пришёл event без focus» либо явно считать такой startup неподдерживаемым.

### Close имеет сознательный компромисс по goroutines

Новая реализация ждёт очистку сессии/хранилища до 5 секунд и публикацию до 250 мс, возвращая ошибку при незавершении. Один зависший callback может продолжить существование после возврата Close; замещающие goroutines не запускаются. Это честно описано и проверено тестом.

Это лучше бесконечно заблокированного Close, но **нельзя одновременно утверждать, что любой Close гарантированно завершил все goroutines**. При ошибке ownership удерживается до настоящего завершения. Если понадобится строгий join-контракт, интерфейс публикации должен сам поддерживать отмену/ограничение времени; произвольную Go-функцию извне принудительно остановить нельзя.

### Семантика Error расширилась относительно исходной v0.2

Исходная спека определяла Error после cleanup. Сейчас Error также означает StopFailed или CleanupFailed при всё ещё удерживаемой сессии. С точки зрения сохранности ресурсов это разумно, но frontend/спецификация должны различать «можно новый Connect» и «ещё нужен recovery». Не следует выводить наличие сессии только из ProcessState.

## Что с concurrency получилось хорошо

### 1. Single writer действительно реализован

`Service.loop` — единственный изменяющий active session, status, revision, failure count и log history. Он принимает команды по `commands` и сообщения worker по `events`. Долгое хранилище, DPAPI, subprocess и сеть вынесены из этого цикла. Это соответствует ADR-003.

`GetStatus` читает `atomic.Value` snapshot и не ждёт `storeMu`. Снимок состоит из значений, а logs возвращаются копией. Mutex для репозитория и callback не противоречит single writer: они защищают другие ресурсы, не альтернативное изменение состояния соединения.

### 2. Владение ресурсами отделено от отмены

Connect резервирует случайный sessionID; session worker владеет startup/process/file cleanup; Disconnect сигнализирует cancel. Новый Connect отклоняется до StopCompleted. Тест с поздним успешным Start после отмены сохраняет единственный Wait и cleanup. Это соответствует базовой идее ADR-004/005.

**Отдельная проверка ревью:** 100 одновременно стартующих вызовов Connect → принят один, запущен один child, Wait выполнен один раз. **5/5** под race detector.

### 3. Нет goroutine на каждое UI-уведомление

Один publisher и канал ёмкостью 1 с вытеснением устаревшего snapshot. Медленный подписчик не блокирует Manager и не создаёт неограниченный хвост goroutines. События состояния для UI допускают объединение; жизненно важные ProcessExited/StopCompleted идут по другому каналу и не выбрасываются.

### 4. Health-check не перекрывается сам с собой

Один последовательный checker на сессию: immediate check, далее ticker 30 секунд, общий timeout 5 секунд. Отмена контекста прерывает сетевой запрос. `probeNetworkVia` ждёт появление TCP-listener короткими ограниченными попытками в общем бюджете и использует полученное соединение для настоящего HTTP-запроса. Наличие порта само по себе не считается успехом.

Новый код readiness изучен статически; его отдельные тесты и Windows-прогоны описаны в репозитории, но не запускались в этой выборке. Тесты неперекрытия health и остановки после Disconnect запускались.

### 5. Native process containment и вывод имеют владельца

На Windows child создаётся внутри Job Object через JOB_LIST, stdout/stderr ограничены whitelist наследуемых handles. Два reader дренируют вывод фиксированными буферами. Wait ожидает выход и readers, закрывает handles; Kill завершает job, синхронизирован mutex с закрытием handles.

Этот код прочитан и скомпилирован под Windows, но не выполнялся в окружении данного ревью. Записанные native-тесты рассматриваются отдельно.

### 6. Новая функция подписок не запирает основной Manager

`app.go` использует отдельные `previewMu`, generation, cancel и срок жизни preview. Сетевая загрузка идёт вне previewMu; после неё проверяются generation/context/closing. Старый результат не может перезаписать новый preview. Candidate consume выполняется под lock, а сохранение отпускает этот lock до диска/DPAPI. Секретная конфигурация остаётся в Go; UI получает metadata и одноразовый ID.

`subscription.go` ограничивает загрузку 15 секундами, 2 MiB и 100 кандидатами. Это статически проверенные свойства, не заявление о полном security-аудите подписок или об исполнении новых тестов в данном ревью.

## Фактическая схема параллельной работы

```text
Wails façade / React commands
        │
        ▼
Service.loop ── atomic snapshot ──► GetStatus
    │
    ├─ session worker: config / preflight / startup / cleanup
    │      ├─ один child.Wait
    │      ├─ один последовательный health checker
    │      └─ Windows adapter: stdout reader + stderr reader
    │                         + context watcher
    │
    ├─ publisher: один callback + coalescing queue(1)
    └─ cleanup waiter: release store lock после loopDone

workers ── session-tagged events ──► Service.loop

Profile Repository: отдельный mutex, без блокирования Manager.
Subscription Preview: отдельная generation/cancel-модель в façade.
Xray: отдельный процесс, сам переносит пользовательский трафик.
```

Количество внутренних goroutines Go, Wails и HTTP runtime не фиксировано этой схемой. Здесь перечислены владельцы логических задач приложения, а не обещание «всегда ровно N goroutines».

## Получилось ли то, что планировали

**Да, по основным решениям:** внешний Xray вместо собственной реализации протоколов; один Go backend; single-writer; session context/ID; один Wait; Job Object; независимые process/network статусы; UI snapshots/events; защищённое хранилище; ограниченные worker и очереди; локальный proxy без системных изменений; закреплённый runtime.

**Частично, по инвариантам жизненного цикла:** модель не запрещает позднее восстановление здорового состояния после ProcessExited; recovery StopFailed не завершён; UI не всегда даёт отправить управляющую команду. Именно это отличает наличие «правильных primitives» от завершённой concurrency-корректности.

**Есть сознательные изменения объёма:**

- По `docs/ACCEPTANCE-SCOPE.md` пользователь сузил цель до Windows 11 x64 с уже установленным WebView2. Windows 10 и missing-WebView2 исключены, их отсутствие не считается новым дефектом и не объявляется PASS.
- Появились ручной импорт подписки и VLESS-ссылки, которых не было в исходном JSON-first MVP. Это расширение функциональности; его отдельный отчёт приёмки существует.
- Новая политика Close/cleanup допускает удержание ресурсов после возврата ошибки и требует отражения в контракте состояний.

## Запуски данного ревью

**Окружение:** Linux amd64, Go 1.23.2. Project go.mod требует Go >=1.26.0 и toolchain 1.26.10; прямой запуск исходного модуля с локальным toolchain отклонён. Файлы production не адаптировались под старый Go: использовалась отдельная оболочка go.mod для выбранного stdlib-only core.

**Выполнено:**

- 39 существующих top-level тестов выбранной подсистемы × 2 с `-race` — PASS. Внутри имеются также subtests.
- `go vet` выбранной подсистемы — PASS.
- Windows amd64 cross-compile выбранных core-тестов — PASS, не native execution.
- Новый event-order regression — FAIL 5/5.
- Новый explicit Stop recovery regression — FAIL 5/5.
- 100 конкурентных Connect — PASS 5/5.

**Не выполнено независимо:** полный Go 1.26.10/Wails build, frontend/Vitest, app façade tests, subscription tests, process readiness tests, native Windows, настоящий Xray и внешние серверы. Npm offline cache также неполон. Локальные успешные результаты не должны заменять эти проверки.

Отсутствие сообщений race detector означает только отсутствие обнаруженных data races в исполненных сценариях. Ошибочный порядок сообщений при безопасной передаче через channels не обязан создавать data race. Именно такой случай показан первым regression-тестом.

## Что добавилось в свидетельствах проекта

`docs/VERIFICATION.md` теперь содержит native Windows 11 результаты, а не только кросс-сборку. В `_bmad-output/backlog/evidence/subscription-acceptance-2026-11-01.md` описан настоящий packaged GUI, пять загруженных кандидатов, один импортированный внешний XHTTP/TLS endpoint, HTTPS через HTTP/SOCKS, отличие egress от прямого baseline и cleanup после Disconnect.

Отчёты отдельно называют dirty source/HEAD и manifests. В этом ревью их выполнение не воспроизводилось; их нельзя автоматически превратить в утверждение, что все проверки исполнены ровно на чистом `eed3550`. Тем не менее это значимый прирост свидетельств работоспособности, и прежнее «Windows вообще не запускался» уже не соответствует содержимому репозитория.

Открыты, согласно текущему scope/отчётам: cross-user DPAPI, остаток native GUI/stress-матрицы, внешние RAW/REALITY и XHTTP/REALITY. Один успешный внешний XHTTP/TLS-сервер не доказывает все оставшиеся сценарии.

## Рекомендуемая очередность

1. Сделать ProcessExited необратимым для health/started-переходов и добавить event-order тест в постоянный набор.
2. Определить и реализовать явный StopFailed recovery, сохранив одного владельца Wait и ресурсов.
3. Развязать UI-профильные мутации и аварийное отключение; проверить это с незавершённым Promise сохранения.
4. После исправлений выполнить целевую Windows stress/acceptance-проверку и обновить документы на точный commit/artifact.

Полная переработка архитектуры не требуется. Требуются завершение нескольких переходов состояния, согласованность UI и регрессионные проверки отказов.
